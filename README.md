# 乱世枭雄

一个 2–12 人的回合制猜拳联机游戏，带着英雄技能那种。起因很简单：我和好久没见的发小想在网上接着玩小时候那种课间猜拳对战的乐子，现成的游戏没有对味的，就自己写了一个。

技术上，它是我想认真做一次的"服务器权威"练习：客户端只发操作，所有结算在服务端完成后广播快照；规则层是纯函数，引擎和英雄插件前后端共用同一份代码。Node.js 22 + TypeScript（strict）+ Socket.IO，前端 Vite + 原生 DOM（没上框架——后来证明这是把双刃剑，见最后）。

## 玩法

多人猜拳定胜负，赢家进行动阶段用英雄技能互殴。支持五元/九元猜拳、蓄力表、随机事件（元素暴走、猝死等），11 人局被我们明确禁止（当年测算下来体验最差，算是个保留的坏趣味）。英雄目前实装 12 个：厨师、吸血鬼、矿工、医生、警察、农夫、木匠、剑客、建造师、铁匠、商人、赌徒。有普通联机（英雄唯一、断线重连、挂机 AI 托管）和沙盒测试房（一人控全场、带回放）两种模式。

## 几个我比较得意的设计

- **插件化英雄**。跨英雄的交互全部走通用令牌和状态数组，代码里没有一处"if 英雄是 XX"的特判。加一个新英雄 = heroes.json 加一条 + 写一个继承基类的策略类 + import 一行，其他什么都不用动。
- **确定性随机数**。用的是 mulberry32，种子状态可序列化。这让崩溃恢复后能接着原来的随机序列跑，录像回放也能一帧不差地复现。
- **规则靠数学不靠感觉**。设计猜拳规则时我写了脚本穷举多人局的重猜率和行动占比，发现"多元素能降低重猜"的直觉是错的——8 人 5 元素重猜率高达 94%。最后定的 B 规则把 8 人局的行动占比从 25~35% 拉到 41~43%，全靠数据说话。

## 实测性能

本机（dev 笔记本）用真实长连接压的，每房 12 条 socket：

- 单实例 2000 房、13183 条连接：吞吐 6314 意图/秒，p99 延迟 0.014ms，全程 0 报错，压完堆从 497MB 完全回收。
- 多实例走 Redis 总线 + 房间分片：双实例聚合 2689 房、三实例峰值 3794 房，error 全 0。

瓶颈试出来是 Node 单线程的事件循环 CPU（吞吐在 6000 出头就到顶了），不是连接数也不是内存。

## 踩过的坑（挑几个记得住的）

- **联网后全场零伤害**。本地自对弈 1000 局都正常，一联网就没人掉血。双根因：建房时漏调了 attachSocket 导致全员被当成离线；另外服务器结算路径没复位回合标志。教训是"两条等价代码路径必须共享同一个状态函数，否则必然漂移"。
- **压 2000 房时以为服务器崩了**。所有健康检查请求全部 fetch failed。查服务端日志发现 rooms=1963、p99 0.014ms、0 error——服务器好得很，是压测客户端自己单进程 CPU 打满，连 HTTP 都发不出去了。于是把压测脚本重写成 master + N worker 多进程。
- **硬刷新后技能按钮全消失**。listHeroes 和 reconnect 两个异步并发，reconnect 先回来时英雄列表还是空的。分布式那边还有个单机永远测不出来的：redis-adapter 首播抛 ClientClosedError 直接把进程崩了，客户端没 connect 就 duplicate 造成的。这类问题只能真机多实例才能抓到。

## 跑起来

```bash
npm install

npm run build   # 构建前端
npm run server  # http://localhost:3001

# 或者开发模式（改前端即时生效，不用手动构建）
npm run dev
```

注意：改了 `client/` 下的代码后如果用 `npm run server`，必须先重新 `npm run build`，否则浏览器加载的还是旧的 `public/dist`——我自己就栽过一次，排查了半天以为技能没实现。

测试：`npm test` 跑全套（类型检查、60 局机器人自对弈、各子系统回归、DB 测试），`npm run test:hero` 单测英雄技能，`npm run test:fe` 跑前端。

## 目前不足

英雄设计稿约 22 个，实装 12 个（有几个机制的纸条还压在学校没拿回来）。前端是千行级的 app.ts 加全局状态，没有组件化，好几个"按钮消失/面板错乱"都源于此；前端测试只有 10 例冒烟，缺 e2e。美术、语音、移动端适配为零。多实例的验证也还受限于只有一台机器。
